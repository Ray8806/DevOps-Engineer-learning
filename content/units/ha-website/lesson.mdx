## 情境

你剛加入一家電商公司，接手他們的購物網站。目前的狀況和需求：

- 網站跑在**一台**虛擬機上，資料庫也只有**一台**，兩者都在同一個可用區。
- 平常有上千位使用者同時在線；促銷活動時流量會變成好幾倍。
- 老闆的要求：**任何一台機器、甚至一整個可用區故障，網站都要能繼續賣東西**；訂單資料不能遺失。
- 預算有限，目前只服務台灣的使用者。

這是雲端架構面試和實務上最常見的題目。這個單元一步步把它改成高可用的架構，最後在 Lab 裡實際動手修好。

## 先找出單點故障

**單點故障**（single point of failure）是指只要它壞掉，整個系統就停擺的元件。逐層檢查目前的架構：

| 元件 | 壞掉時 | 問題 |
|---|---|---|
| 唯一的網頁伺服器 | 網站完全無法連線 | 沒有備援，也撐不住促銷流量 |
| 唯一的資料庫 | 無法下單，資料可能遺失 | 沒有備用執行個體 |
| 唯一的可用區 | 上面兩個一起停 | 斷電、網路故障會同時影響所有元件 |

AWS Well-Architected 的建議是：正式環境的工作負載至少要部署在一個區域的**兩個可用區**。可用區之間在實體上分開、各有獨立的電力和網路，又近到可以同步複寫資料。

## 一步步改進

### 1. 網頁伺服器：多台、跨可用區、放在負載平衡器後面

- 用**負載平衡器**當唯一的入口，它只把請求送給健康檢查通過的機器。
- 網頁伺服器改由**自動擴展群組**管理（AWS 的 Auto Scaling 群組、Google Cloud 的 MIG），分散在至少兩個可用區，設定最少台數，壞掉的機器會被自動替換。
- 加上**自動擴展政策**（例如維持平均 CPU 50%），促銷時自動加機器、結束後自動減少，不用事先猜要準備多少台。

這也是可靠性設計的原則：**水平擴展**，用多台小機器取代一台大機器，單一機器故障的影響就變小。

### 2. 讓網頁伺服器變成無狀態

有了很多台機器，使用者的下一個請求可能被送到另一台。如果登入狀態、購物車只存在某一台機器的記憶體或磁碟，換一台就不見了，那台壞掉時也會一起消失。

解法是讓網頁伺服器**無狀態**（stateless）：工作階段（session）資料放到共用的**快取**或資料庫，使用者上傳的圖片放到**物件儲存**。這樣任何一台都能處理任何請求，機器可以隨時替換、隨時增減。

### 3. 資料庫：高可用加上唯讀複本

- 開啟資料庫的**高可用**設定（RDS Multi-AZ、Cloud SQL 的 REGIONAL）：在另一個可用區準備備用執行個體、同步複寫，主要的故障時自動容錯移轉，應用程式使用同一個連線位址。
- 讀取量大時加上**唯讀複本**分擔查詢。注意兩者的用途不同：備用執行個體負責接手，唯讀複本負責分擔讀取。
- 備份照常要做：高可用防的是故障，防不了誤刪資料。

### 4. 靜態檔案與快取

- 圖片、CSS、JavaScript 放在**物件儲存**，前面加上 **CDN**：使用者從最近的節點拿到檔案，網頁伺服器的負擔也減輕。
- 常被讀取、不常變動的資料（例如商品清單）放進**快取**，減少對資料庫的查詢。資料庫一時過載時，快取還能先回應，讓網站降級運作而不是完全停擺。

### 5. 耗時的工作交給佇列

下單後的寄信、產生發票、通知倉庫，不需要讓使用者等。把它們放進**訊息佇列**，由背景的工作者處理：促銷尖峰時訊息先堆在佇列裡，寄信服務暫時故障也不會讓下單失敗。

### 6. 安全與監控

- 網頁伺服器和資料庫放在**私有子網路**，只有負載平衡器面對網際網路；資料庫只接受網頁伺服器的連線。
- 在負載平衡器前加上 **WAF**，擋掉常見的攻擊和惡意來源。
- 監控健康檢查、錯誤率和延遲，設定警示；並且**定期演練**：故意關掉一台機器、觸發資料庫容錯移轉，確認架構真的撐得住。

### AWS 的架構

| 層 | 服務與設定 |
|---|---|
| DNS | Route 53，網域指到 CloudFront 和 ALB（別名紀錄） |
| 靜態檔案 | S3 + CloudFront |
| 防護 | AWS WAF 的 web ACL 關聯到 ALB |
| 入口 | Application Load Balancer，子網路在兩個以上的可用區 |
| 網頁伺服器 | 啟動範本 + Auto Scaling 群組：子網路分布在多個可用區、最少 2 台、目標追蹤擴展政策；健康檢查類型可以用 ELB，讓應用程式沒有回應的執行個體也被替換 |
| 工作階段與快取 | ElastiCache（Valkey、Redis OSS 或 Memcached）。可以用 Serverless，或節點型叢集並選擇 Multi-AZ |
| 資料庫 | RDS Multi-AZ（同步複寫的備用執行個體、自動容錯移轉），需要時加唯讀複本；放在私有子網路的 DB 子網路群組 |
| 背景工作 | SQS 佇列 + 工作者（EC2 或 Lambda） |
| 監控 | CloudWatch 指標與警示 |

```bash
# 讓 Auto Scaling 群組跨兩個可用區
aws autoscaling update-auto-scaling-group --auto-scaling-group-name shop-asg \
  --vpc-zone-identifier "subnet-a,subnet-b" --min-size 2 --max-size 6 --desired-capacity 2
# 資料庫改成 Multi-AZ，立刻套用
aws rds modify-db-instance --db-instance-identifier shop-db --multi-az --apply-immediately
```

### Google Cloud 的架構

| 層 | 服務與設定 |
|---|---|
| DNS | Cloud DNS，網域指到負載平衡器的 IP |
| 靜態檔案 | Cloud Storage 的後端 bucket，開啟 Cloud CDN |
| 防護 | Cloud Armor 安全政策掛到後端服務 |
| 入口 | 全域外部 Application Load Balancer（一個 anycast IP） |
| 網頁伺服器 | 執行個體範本 + **regional MIG**（預設把 VM 分散在區域內的三個可用區）、自動擴展、自動修復；也可以在不同可用區建多個 zonal MIG，都加為後端服務的後端 |
| 工作階段與快取 | Memorystore for Redis Standard Tier：高可用、複本分散在不同可用區、99.9% 的 SLA |
| 資料庫 | Cloud SQL 高可用（REGIONAL）：兩個可用區、自動容錯移轉；需要時加唯讀複本 |
| 背景工作 | Pub/Sub + 訂閱者（Compute Engine 或 Cloud Run） |
| 監控 | Cloud Monitoring 指標、正常運作時間檢查與快訊政策 |

別忘了：防火牆要允許 Google 健康檢查的來源 IP 範圍（`35.191.0.0/16`），否則所有後端都會被判定為不健康。

```bash
# 在另一個可用區加上後端
gcloud compute instance-groups managed create shop-mig-c --template=shop-template \
  --size=1 --zone=asia-east1-c
gcloud compute backend-services add-backend shop-backend --instance-group=shop-mig-c \
  --instance-group-zone=asia-east1-c --global
# 資料庫改成高可用
gcloud sql instances patch shop-db --availability-type=REGIONAL
```

## 設計上的取捨

- **跨區域要不要做？** 跨可用區已經能撐過單一資料中心的故障。AWS Well-Architected 把「明明跨可用區就滿足需求，卻做了跨區域架構」列為常見的錯誤：跨區域要複製整套環境，成本和複雜度都高很多。需要撐過整個區域故障時，請看「災難復原」的做法。
- **成本**：資料庫高可用的費用大約是單機的兩倍（Cloud SQL 的說明就是兩倍），網頁伺服器至少兩台。用自動擴展讓離峰時只維持最少台數。
- **快取的一致性**：快取的資料可能不是最新的。商品清單晚幾秒更新沒關係，庫存和付款就要直接查資料庫。

## 面試時怎麼回答

被問到「設計一個高可用的網站」時，可以照這個順序：

1. **先問需求**：使用者有多少、在哪裡？可以接受停機多久？資料可以遺失多少？預算？
2. **找單點故障**：從使用者到資料庫，每一層壞掉會怎樣。
3. **逐層加上備援**：負載平衡器 + 跨可用區的自動擴展群組、無狀態的伺服器、資料庫高可用。
4. **處理擴展**：自動擴展、快取、CDN、唯讀複本、用佇列處理耗時的工作。
5. **安全與營運**：私有子網路、WAF、監控與警示、定期演練。
6. **說明取捨**：為什麼不跨區域、成本多少。

## 重點整理

- 先找出單點故障：只有一台、只在一個可用區的元件都是。
- 網頁伺服器：負載平衡器 + 跨至少兩個可用區的自動擴展群組，最少兩台，壞掉自動替換。
- 伺服器要無狀態：工作階段放快取或資料庫，檔案放物件儲存。
- 資料庫開高可用（另一個可用區的備用執行個體、自動容錯移轉），讀取量大再加唯讀複本；備份照常做。
- 靜態檔案用物件儲存 + CDN；常讀的資料放快取；耗時的工作交給佇列。
- 跨可用區通常就夠了，跨區域留給真的需要撐過整個區域故障的系統。
