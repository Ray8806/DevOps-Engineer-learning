## 兩個問題：你是誰、你能做什麼

雲端上的每一個操作，背後都會先確認兩件事：

- **驗證**（authentication）：你是誰？例如用密碼加上手機驗證碼登入。
- **授權**（authorization）：你可以做什麼？例如可以讀取某個 bucket，但不能刪除。

負責這兩件事的服務叫 **IAM**（Identity and Access Management，身分與存取管理）。不管是人從主控台點按鈕，還是程式呼叫 API，都要通過 IAM 的檢查。

## 身分不只是人

需要權限的不只有使用者，還有**程式**。一台虛擬機上的應用程式要讀取儲存服務裡的檔案，它也需要一個身分。

| 身分的種類 | 例子 |
|---|---|
| 人 | 工程師、財務人員 |
| 群組 | 把多個人放在一起，一次授權 |
| 給程式用的身分 | 虛擬機上的應用程式、排程工作 |

<Callout title="不要把金鑰寫進程式">
讓程式取得權限最危險的做法，是把長期有效的金鑰寫在程式碼或設定檔裡。金鑰一旦跟著程式碼外流，拿到的人就擁有同樣的權限。兩個平台都提供「把身分直接掛在運算資源上」的做法，程式會自動取得短期憑證，不需要保管任何金鑰。
</Callout>

## 最小權限原則

**只給完成工作所需的權限，不多給。** 這是 IAM 最重要的一條原則。

權限給太大，平常看不出問題，但帳號被盜用或程式有漏洞時，損害範圍就是那個身分擁有的全部權限。只需要讀取報表的人，就不該擁有刪除資料庫的權限。

實務上的做法：

- 從現成的權限組合開始，再逐步縮小到實際需要的範圍。
- 把權限授予群組，而不是一個一個使用者設定。
- 定期檢查並移除不再使用的身分和權限。
- 為所有人啟用多重要素驗證（MFA）。

### AWS IAM

AWS 的 IAM 有四個核心元件：

| 元件 | 說明 |
|---|---|
| 使用者（user） | 代表一個人或一個應用程式，擁有長期憑證 |
| 群組（group） | 使用者的集合，用來一次授予相同的權限 |
| 角色（role） | 可以被「擔任」的身分，提供自動輪替的臨時憑證 |
| 政策（policy） | 以 JSON 寫成的文件，描述允許或拒絕哪些操作 |

**政策**決定權限。把政策附加到使用者、群組或角色上，它們才有權限做事。AWS 提供許多現成的**受管政策**，例如 `AmazonS3ReadOnlyAccess`。

**角色**是給程式用的首選。把角色附加到 EC2 執行個體上，上面的應用程式就能取得臨時憑證，不必保存任何金鑰。

**root 使用者**是建立 AWS 帳戶時的那個身分，擁有無法限制的完整權限。AWS 的建議是：為它啟用 MFA，不要用它做日常工作。

AWS 目前的最佳實務還包括：人員盡量透過身分提供者以臨時憑證登入，而不是為每個人建立長期的 IAM 使用者；工作負載一律使用角色。

**常用指令**

```bash
# 建立群組
aws iam create-group --group-name developers

# 把受管政策附加到群組
aws iam attach-group-policy --group-name developers --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess

# 建立使用者，並加入群組
aws iam create-user --user-name alice
aws iam add-user-to-group --group-name developers --user-name alice

# 查看群組附加了哪些政策
aws iam list-attached-group-policies --group-name developers
```

### Google Cloud IAM

Google Cloud 的授權可以用一句話描述：**誰**（主體）在**哪個資源**上擁有**什麼角色**。

| 元件 | 說明 |
|---|---|
| 主體（principal） | 被授權的對象：Google 帳戶、群組、服務帳戶 |
| 角色（role） | 一組權限的集合 |
| 允許政策（allow policy） | 附加在資源上，記錄哪些主體擁有哪些角色 |

角色分成三種：

| 種類 | 說明 |
|---|---|
| 基本角色 | 範圍非常大，涵蓋所有服務的上千個權限。目前是 Admin、Writer、Reader；Owner、Editor、Viewer 是較早的舊版基本角色 |
| 預先定義的角色 | 由 Google 維護，針對特定服務提供細緻的權限，例如 `roles/storage.objectViewer` |
| 自訂角色 | 由你自己指定要包含哪些權限 |

Google 的建議是：正式環境不要授予基本角色，改用預先定義或自訂的角色。

**服務帳戶**是給程式用的身分，以電子郵件位址識別。把服務帳戶附加到 Compute Engine 執行個體上，應用程式就能以它的身分呼叫 API。服務帳戶金鑰是可以下載的長期憑證，管理不當就是資安風險，能避免就避免。

**資源階層**會影響權限：機構 → 資料夾 → 專案 → 資源。在上層授予的角色會**往下繼承**，所以在專案上給的角色，對專案裡所有的資源都有效。

**常用指令**

```bash
# 建立服務帳戶
gcloud iam service-accounts create app-reader --display-name="App reader"

# 在專案上把角色授予服務帳戶
gcloud projects add-iam-policy-binding my-project --member="serviceAccount:app-reader@my-project.iam.gserviceaccount.com" --role="roles/storage.objectViewer"

# 查看專案的允許政策
gcloud projects get-iam-policy my-project

# 移除一筆授權
gcloud projects remove-iam-policy-binding my-project --member="user:intern@example.com" --role="roles/editor"
```

## 兩個平台的差異

<Compare />

兩邊最容易混淆的是「角色」這個詞：在 AWS，角色是一種**身分**，可以被擔任；在 Google Cloud，角色是一組**權限**。Google Cloud 裡對應 AWS 角色的東西是服務帳戶。

## 重點整理

- 驗證是確認你是誰，授權是決定你能做什麼。
- 身分包含人、群組，以及給程式用的身分。
- 最小權限原則：只給完成工作所需的權限。
- 程式不要使用長期金鑰：AWS 用角色，Google Cloud 用服務帳戶附加到運算資源上。
- AWS 把政策附加到身分上；Google Cloud 在資源上把角色繫結給主體，而且會沿著資源階層往下繼承。
- 權限範圍太大的選項要避開：AWS 的 root 使用者不做日常工作，Google Cloud 的基本角色不用在正式環境。
