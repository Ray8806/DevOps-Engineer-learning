## 什麼是無伺服器運算

用虛擬機架一個網站，你要選規格、裝作業系統、打更新、決定開幾台，而且就算半夜沒有人用，機器還是在跑、還是在收費。

**無伺服器運算**（serverless）把這些都交給雲端供應商。你只交出**程式碼**或**容器映像檔**，平台負責：

- 準備執行環境、更新作業系統。
- 有請求進來時自動啟動、流量變大時自動增加執行個體。
- 沒有流量時縮減，甚至**縮到零**。
- 依實際的使用量計費，而不是依開機時間。

「無伺服器」不是真的沒有伺服器，而是**伺服器不歸你管**。

## 適合和不適合的工作

| 適合 | 不太適合 |
|---|---|
| 網站後端 API、Webhook | 需要一直佔用大量 CPU、全天滿載的工作 |
| 有檔案上傳時自動處理（縮圖、轉檔） | 要在本機磁碟長期保存資料的程式 |
| 排程工作（每天整理一次資料） | 需要特定作業系統設定或核心模組的軟體 |
| 流量忽高忽低、常常沒人用的服務 | 單次執行時間超過平台上限的長時間工作 |

## 幾個一定要懂的觀念

**事件驅動**：無伺服器的程式通常是「被叫起來」的。觸發的來源可以是 HTTP 請求、有檔案上傳到物件儲存、佇列裡有新訊息、排程時間到了。

**無狀態**：每次請求可能由不同的執行環境處理，執行環境也可能隨時被回收。所以不要把資料存在記憶體或本機磁碟，要存到資料庫或物件儲存。

**冷啟動**：如果目前沒有可用的執行環境，平台要先建立一個（載入程式碼、初始化），第一個請求會比較慢，這叫做**冷啟動**。兩個平台都可以預先保留幾個已經初始化好的環境來避免冷啟動，但這些環境即使閒置也會收費。

**逾時**：每次執行都有時間上限。超過上限，平台會中斷它。

**權限**：程式在雲端上執行時，用的是你指定的**身分**（AWS 的執行角色、Google Cloud 的服務帳戶）。依最小權限原則，只給它需要的權限。

<Callout title="沒有流量也可能收費的情況">
縮到零之後就不收運算費用，但只要你設定了「至少保持幾個執行環境」，那些環境就會一直收費。練習完記得把這類設定調回 0，或直接刪除服務。
</Callout>

### AWS Lambda

Lambda 是 AWS 的無伺服器運算服務。你寫一個**處理函式**（handler），把它接到觸發來源，Lambda 就會在事件發生時執行它。每次呼叫各自獨立、不共用狀態。

<Callout title="Lambda 的三種形式">
最常見的 Lambda 函式現在正式稱為 **Lambda Event Functions**（事件函式），這個單元說的就是它。AWS 另外推出了 Lambda Web Functions（直接執行 Node.js 網頁伺服器）和 Lambda MicroVMs（每個使用者一個獨立的執行環境），不過 `aws lambda create-function`、`invoke` 等 API 和指令都沒有改變。
</Callout>

**處理函式**：以 Python 為例，檔案 `lambda_function.py` 裡有一個 `lambda_handler(event, context)` 函式，處理函式的設定就寫成 `lambda_function.lambda_handler`（檔名加上函式名稱）。`event` 是觸發來源傳進來的資料。

**部署套件**：程式碼和相依套件壓縮成 `.zip` 檔上傳；也可以改用容器映像檔。

**執行角色**：每個函式都要指定一個 IAM 角色，Lambda 執行函式時會**扮演**這個角色。角色的信任政策必須允許 `lambda.amazonaws.com` 扮演它。AWS 受管政策 `AWSLambdaBasicExecutionRole` 提供寫入 CloudWatch 日誌的權限，是最基本的選擇；函式要讀 S3 或寫 DynamoDB，就要再加上對應的權限。

**重要的設定與限制**

| 項目 | 預設值 | 範圍 |
|---|---|---|
| 逾時 | 3 秒 | 1 到 900 秒（15 分鐘） |
| 記憶體 | 128 MB | 128 MB 到 10,240 MB，CPU 依記憶體比例分配 |
| `/tmp` 暫存空間 | | 512 MB 到 10,240 MB |
| 部署套件（.zip） | | 直接上傳最多 50 MB，解壓縮後最多 250 MB |
| 容器映像檔 | | 最多 10 GB |
| 每個 Region 的同時執行數 | 1,000（帳戶配額，新帳戶可能較低） | 可申請提高 |

**計費**：依**請求次數**加上**執行時間乘以記憶體**（GB-秒）計費。記憶體設得越大，每秒越貴，但 CPU 也越多、可能跑得越快。

**並行與冷啟動**：一個執行環境預設一次只處理一個請求，同時有 10 個請求就需要 10 個執行環境。**保留並行**（reserved concurrency）限制某個函式最多能用多少執行環境；**佈建並行**（provisioned concurrency）事先初始化好一定數量的環境，可以減少冷啟動，但要另外收費。

**用 HTTP 呼叫**：可以替函式建立**函式網址**（function URL），驗證方式選 `AWS_IAM` 或 `NONE`；需要更多 API 管理功能時用 API Gateway。

**常用指令**

```bash
# 建立執行角色（trust-policy.json 允許 lambda.amazonaws.com 扮演），再附加基本的日誌權限
aws iam create-role --role-name lambda-basic-role --assume-role-policy-document file://trust-policy.json
aws iam attach-role-policy --role-name lambda-basic-role --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole

# 打包程式碼並建立函式
zip function.zip lambda_function.py
aws lambda create-function --function-name hello --runtime python3.14 --handler lambda_function.lambda_handler --role arn:aws:iam::123456789012:role/lambda-basic-role --zip-file fileb://function.zip

# 呼叫函式，回應寫進 response.json
aws lambda invoke --function-name hello --cli-binary-format raw-in-base64-out --payload '{"name": "Ray"}' response.json

# 調整逾時與記憶體
aws lambda update-function-configuration --function-name hello --timeout 30 --memory-size 256
```

`--cli-binary-format raw-in-base64-out` 是因為 AWS CLI 第 2 版預設把 `--payload` 當成 base64 編碼的資料；直接傳 JSON 時要加上這個選項。

### Cloud Run

Cloud Run 是 Google Cloud 的全代管應用程式平台：只要能做成**容器映像檔**，任何語言都能部署。使用 Go、Node.js、Python、Java、.NET、Ruby 等語言時，也可以直接交出原始碼，讓 Cloud Run 幫你建置容器。

Cloud Run 有四種資源：

| 資源 | 用途 |
|---|---|
| 服務（service） | 回應 HTTP 請求，有固定的 HTTPS 網址，自動擴展 |
| 工作（job） | 執行到完成就結束的工作，可以手動或排程執行 |
| 工作站集區（worker pool） | 一直在背景執行的工作，例如處理訊息佇列 |
| 執行個體（instance） | 需要單一、長時間執行環境的工作 |

**服務的網址**：每個服務都有一個 `*.run.app` 的 HTTPS 網址，格式是 `https://服務名稱-專案編號.區域.run.app`，Cloud Run 會幫你管理 TLS 憑證。

**修訂版本**（revision）：每次部署或修改設定，都會建立一個新的、**不能修改**的修訂版本。可以把流量逐步轉到新版本（例如先給 1%），也可以退回舊版本。

**重要的設定與預設值**

| 項目 | 預設值 | 範圍 |
|---|---|---|
| 請求逾時 | 5 分鐘 | 最多 60 分鐘 |
| 記憶體 | 512 MiB | 最多 32 GiB |
| 每個執行個體同時處理的請求 | 用 gcloud 建立時是 80 × vCPU 數 | 最多 1,000 |
| 最多執行個體 | 每個修訂版本 100 | 可以調整 |
| 最少執行個體 | 0（沒有流量時縮到零） | 設定大於 0 可以減少冷啟動 |

和 Lambda 不同，**一個 Cloud Run 執行個體可以同時處理很多個請求**，所以通常需要的執行個體比較少。

**計費**：預設是**依請求計費**，只有執行個體在處理請求時才收費；也可以改成**依執行個體計費**，整個執行個體存活期間都收費，適合在請求以外還要做背景工作的服務。

**誰可以呼叫**：Cloud Run 預設會做 **Invoker IAM 檢查**，只有擁有 `roles/run.invoker` 的身分能呼叫。要公開給所有人，Google 建議**關閉 Invoker IAM 檢查**（`--no-invoker-iam-check`）；另一個做法是把 `roles/run.invoker` 授權給 `allUsers`（`--allow-unauthenticated` 就是這樣做）。

### Cloud Run functions

只想寫一個函式、不想處理容器時，可以用 **Cloud Run functions**（以前叫 Cloud Functions）。現在的函式會自動建置成容器，**以 Cloud Run 服務的形式部署**，所以 Cloud Run 的設定（記憶體、並行、最少執行個體等）都適用。舊版的函式稱為 Cloud Run functions（第 1 代），觸發方式、執行環境和可調整的設定都比較有限。

**常用指令**

```bash
# 用 Google 提供的範例映像檔部署服務，並允許所有人呼叫
gcloud run deploy hello --image=us-docker.pkg.dev/cloudrun/container/hello --region=asia-east1 --allow-unauthenticated

# 修改設定會建立新的修訂版本
gcloud run services update hello --region=asia-east1 --update-env-vars=GREETING=hello
gcloud run services update hello --region=asia-east1 --max-instances=5

# 查看服務與修訂版本
gcloud run services describe hello --region=asia-east1
gcloud run revisions list --service=hello --region=asia-east1

# 刪除服務
gcloud run services delete hello --region=asia-east1
```

## 兩個平台的差異

<Compare />

最值得記住的差別是**並行**：Lambda 的一個執行環境預設一次處理一個請求；Cloud Run 的一個執行個體可以同時處理很多個請求。另外，Lambda 交出去的是函式，Cloud Run 交出去的是容器。

## 重點整理

- 無伺服器運算把伺服器交給供應商管理，依流量自動擴展、可以縮到零、依用量計費。
- 程式要設計成無狀態，資料存在資料庫或物件儲存。
- 冷啟動會讓第一個請求變慢；預先保留執行環境可以改善，但會持續收費。
- 每次執行都有逾時上限：Lambda 預設 3 秒、最多 15 分鐘；Cloud Run 預設 5 分鐘、最多 60 分鐘。
- Lambda 要指定執行角色，角色的信任政策要允許 `lambda.amazonaws.com`。
- Cloud Run 每次修改設定都會建立新的修訂版本，可以分流和退回。
- Cloud Run 預設只允許有 `roles/run.invoker` 的身分呼叫，公開服務要明確設定。
