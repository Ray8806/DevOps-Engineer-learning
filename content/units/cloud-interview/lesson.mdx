## 怎麼使用這個單元

這個單元整理雲端工程師面試常見的題目。每一題都**先自己想、最好說出來**，再按「看回答重點」對照。回答重點不是要背的標準答案，而是面試官通常想聽到的幾個關鍵；題目下面也會標出對應的單元，答不出來就回去複習。

雲端工程師的面試通常有四種題型：

| 題型 | 在考什麼 | 例子 |
|---|---|---|
| 觀念題 | 你懂不懂基本元件、能不能講清楚差別 | 安全群組和網路 ACL 有什麼不同？ |
| 情境設計題 | 能不能從需求出發，設計出合理的架構並說明取捨 | 設計一個高可用的網站 |
| 故障排除題 | 遇到問題時，能不能有系統地縮小範圍 | 負載平衡器後面的機器全部不健康 |
| 行為題 | 你怎麼和人合作、怎麼面對錯誤 | 說說你處理過最嚴重的事故 |

## 觀念題

回答觀念題的訣竅：**先講一句話的定義，再講差別或用途，最後舉一個例子**。不要只背名詞。

### 區域和可用區有什麼不同？為什麼要跨可用區部署？

<Answer>

- **區域**（region）是一個地理位置，裡面有多個**可用區**（availability zone）。
- 可用區之間在實體上分開、各有獨立的電力和網路，所以一場火災或停電通常只影響一個可用區；它們又夠近，可以用低延遲的網路同步複寫資料。
- 只在一個可用區的系統，那個可用區出問題就整個停擺；所以正式環境至少放在兩個可用區。
- 加分：補充「跨可用區防的是資料中心層級的故障；整個區域故障要靠災難復原」。

複習：虛擬機、案例：高可用網站

</Answer>

### 安全群組（或 VPC 防火牆規則）和 AWS 的網路 ACL 有什麼不同？

<Answer>

- 關鍵字是**有狀態**和**無狀態**：安全群組、Google Cloud 的 VPC 防火牆規則都是有狀態的，允許了進來的連線，回應會自動放行；網路 ACL 是無狀態的，回應流量也要明確允許。
- 安全群組套用在執行個體（網路介面）上；網路 ACL 套用在子網路上，適合當成第二道防線，例如封鎖某段 IP。
- 常見錯誤：說「網路 ACL 比較安全所以都用它」。實務上主要靠安全群組。

複習：虛擬網路

</Answer>

### 公有子網路和私有子網路差在哪？私有子網路裡的機器要怎麼下載套件？

<Answer>

- 差別在**路由**：公有子網路的路由表有一條指向網際網路閘道的路由；私有子網路沒有，外面無法直接連進來。
- 私有子網路的機器要連出去（例如下載更新），透過 **NAT**：AWS 的 NAT 閘道、Google Cloud 的 Cloud NAT。NAT 只讓裡面的機器主動連出去，外面還是連不進來。
- 資料庫、應用程式伺服器放私有子網路，只有負載平衡器面對網際網路。

複習：虛擬網路

</Answer>

### 為什麼程式應該用「角色」或服務帳戶，而不是把存取金鑰寫在程式裡？

<Answer>

- 金鑰寫在程式或設定檔裡，很容易隨著程式碼外洩，而且是長期有效的。
- **角色**（AWS）或**服務帳戶**（Google Cloud）讓程式取得**自動輪替的臨時憑證**，不用保存任何金鑰。
- 搭配**最小權限原則**：只給完成工作需要的權限。外部的 CI 工具則用 OIDC 換取短期憑證。

複習：身分與權限、CI/CD

</Answer>

### 第 4 層和第 7 層的負載平衡差在哪？什麼時候用哪一種？

<Answer>

- 第 4 層（傳輸層）看 IP 和連接埠轉送 TCP、UDP；第 7 層（應用層）看得懂 HTTP，可以依路徑、主機名稱轉送。
- 一般的網站和 API 用第 7 層（AWS 的 ALB、Google Cloud 的 Application Load Balancer）；非 HTTP 的協定或需要極高效能時用第 4 層（AWS 的 NLB）。
- 不論哪一種，負載平衡器都會做健康檢查，只把流量送給健康的機器。

複習：負載平衡與自動擴展

</Answer>

### 資料庫的「高可用備用執行個體」和「唯讀複本」有什麼不同？

<Answer>

- 備用執行個體在另一個可用區、**同步**複寫，主要的故障時**自動容錯移轉**；它負責接手，不分擔讀取（RDS Multi-AZ 的 DB 執行個體部署、Cloud SQL 高可用）。
- 唯讀複本用來**分擔讀取**，通常要手動升格才能接手寫入；跨區域的唯讀複本也可以當作災難復原的準備。
- 加分：兩者可以一起用；而且高可用防不了誤刪資料，還是要備份。

複習：關聯式資料庫、案例：災難復原

</Answer>

### 容器和虛擬機有什麼不同？

<Answer>

- 虛擬機各自有完整的作業系統；容器**共用主機的作業系統核心**，所以更輕量、啟動更快。
- 容器把程式和它需要的東西打包成**映像檔**，在哪裡跑都一樣，解決「在我的電腦上可以跑」的問題。
- 隔離程度是虛擬機比較強；兩者也常一起用：容器跑在虛擬機上。

複習：容器

</Answer>

### Kubernetes 的 Deployment 和 Service 各負責什麼？

<Answer>

- **Deployment** 描述用哪個映像檔、要幾份：維持 Pod 的數量、擴展，換版本時做**滾動更新**，出問題可以回復。
- **Pod** 會被替換、IP 會變，所以需要 **Service**：提供穩定的 IP 和名稱，用標籤選擇器找到 Pod，把請求負載平衡過去；`LoadBalancer` 類型的 Service 讓叢集外也連得到。

複習：Kubernetes

</Answer>

### 什麼是基礎架構即程式碼（IaC）？什麼是偏移？

<Answer>

- 把雲端資源寫成檔案：可以版本控制、用 pull request 審查、重複部署出一樣的環境。工具大多是**宣告式**的：描述想要的結果，工具比較後決定要建立、修改還是刪除。
- **偏移**（drift）：有人在 IaC 之外手動改了資源，實際狀態和程式碼不一致。用 `terraform plan` 或 CloudFormation 的偏移偵測找出來。
- 好習慣：永遠先看計畫（`plan`、變更集）再套用。

複習：基礎架構即程式碼

</Answer>

### 訊息佇列說「至少傳送一次」，寫程式時要注意什麼？

<Answer>

- 同一則訊息可能被收到不只一次，而且不保證順序。
- 處理要**冪等**（重複執行也沒關係），例如用訂單編號檢查是否已經處理過。
- 也要設定好可見性逾時（SQS）或確認期限（Pub/Sub），處理完才刪除或確認；一直失敗的訊息交給 dead-letter。

複習：訊息佇列

</Answer>

### 網站更新了圖片，使用者卻還是看到舊的。為什麼？怎麼處理？

<Answer>

- CDN 會依 TTL 把檔案快取在節點上，快取還沒過期就會繼續提供舊的檔案。
- 處理方式：**清除快取**（invalidation，例如 `/images/*`），或在檔名加上版本號讓網址改變，或調整 `Cache-Control` 讓會變動的檔案快取短一點。

複習：DNS 與 CDN

</Answer>

### RTO 和 RPO 是什麼？

<Answer>

- **RTO**：可以接受停機多久；**RPO**：可以接受遺失多久的資料。
- 由業務影響和成本決定，再選備份還原、pilot light、warm standby 或 active/active。
- 常見錯誤：把兩者講反，或說「RTO、RPO 都要是零」而不談成本。

複習：案例：災難復原

</Answer>

### 雲端的帳單越來越高，你會怎麼控制成本？

<Answer>

1. **先看清楚**：依服務、依**標籤**（團隊、專案、環境）看費用，知道錢花在哪裡。
2. **設預算與通知**，用預測金額提前警告。
3. **找浪費**：沒掛載的磁碟、舊快照、閒置的 IP、規格過大的機器、非上班時間還開著的測試環境。
4. **用對買法**：穩定的用量用 Savings Plans 或承諾使用折扣；可以中斷的工作用 Spot。

複習：成本管理

</Answer>

## 情境設計題

情境設計題沒有唯一的答案，面試官看的是**思考過程**。建議的順序：

1. **先問需求**：使用者多少、在哪裡？可以接受停機多久、遺失多少資料？預算？
2. **畫出最簡單能動的版本**，再找出單點故障和瓶頸。
3. **逐層改進**：運算、資料、網路、安全、監控。
4. **主動說明取捨**：為什麼選這個、不選那個，成本多少。

### 設計一個高可用的購物網站

<Answer>

- 負載平衡器 + 跨至少兩個可用區的自動擴展群組；網頁伺服器**無狀態**（工作階段放快取或資料庫）。
- 資料庫開高可用，讀取量大加唯讀複本，照常備份。
- 靜態檔案放物件儲存 + CDN；耗時的工作交給佇列。
- 私有子網路、WAF、監控與警示、定期演練。
- 跨區域通常不需要，除非要撐過整個區域故障。

完整的思路請看「案例：高可用網站」。

</Answer>

### 設計一個每天匯入分店銷售資料、讓分析人員用 SQL 查詢的系統

<Answer>

- 收集 → 儲存原始資料（資料湖）→ 處理 → 分析。
- 新檔案上傳觸發事件通知，交給佇列或 Pub/Sub，處理程式要能承受重複的事件；處理結果寫到別的位置，避免無限迴圈。
- 用分區和欄式格式降低查詢掃描的資料量（Athena、BigQuery 都依處理的資料量計費）。

完整的思路請看「案例：資料管線」。

</Answer>

### 使用者上傳照片後，要自動產生縮圖。你會怎麼設計？

<Answer>

- 照片上傳到物件儲存的「原圖」位置；上傳完成觸發**事件通知**，交給函式（例如 Lambda、Cloud Run functions）或佇列後面的工作者產生縮圖。
- 縮圖寫到**另一個 bucket 或另一個前綴**，避免縮圖本身又觸發事件形成無限迴圈。
- 事件可能重複：同一張照片處理兩次只是覆寫同一個縮圖，結果一樣（冪等）。
- 大量上傳時用佇列吸收尖峰；處理失敗的交給 dead-letter，修好後重新處理。
- 使用者看縮圖透過 CDN。

複習：無伺服器、物件儲存、訊息佇列、案例：資料管線

</Answer>

### 公司要求整個區域故障時，一小時內恢復服務、最多遺失五分鐘的資料。你會怎麼做？

<Answer>

- RTO 一小時、RPO 五分鐘：只靠每日備份達不到 RPO；備份還原整個環境也可能來不及。
- 適合 **pilot light** 或 **warm standby**：資料庫用跨區域唯讀複本持續複寫，環境用 IaC 在備援區域預先建好（或縮小版先開著）。
- 切換步驟：升格複本、啟動或擴大應用程式、用 DNS 或全域負載平衡切流量，最後替新的主要資料庫建立新的備援。
- 還要有時間點備份防資料損毀，並定期演練量測實際的 RTO、RPO。

完整的思路請看「案例：災難復原」。

</Answer>

## 故障排除題

回答故障排除題時，展現**有系統的方法**比直接猜答案重要：

1. **確認現象與範圍**：所有人都壞，還是部分？什麼時候開始？最近改了什麼？
2. **沿著請求的路徑由外往內查**：DNS → 負載平衡器 → 執行個體 → 應用程式 → 資料庫。
3. **看證據**：指標、日誌、健康檢查的狀態，而不是憑感覺。
4. **一次只改一個地方**，確認效果；事後寫檢討，避免再發生。

### 負載平衡器後面的機器都在跑，健康檢查卻全部失敗

<Answer>

- 先確認健康檢查的**連接埠和路徑**對不對（例如 `/health` 有沒有回應 200）。
- 檢查防火牆：Google Cloud 要允許健康檢查的來源 IP 範圍（`35.191.0.0/16`），否則所有後端都被判定不健康；AWS 要確認執行個體的安全群組允許負載平衡器連進來。
- 還在開機的機器可能被誤判：設定健康檢查的寬限期。

複習：負載平衡與自動擴展

</Answer>

### 私有子網路裡的機器無法下載套件更新

<Answer>

- 私有子網路沒有到網際網路閘道的路由，要透過 NAT 才能連出去。
- 檢查：有沒有 NAT 閘道（AWS 的 NAT 閘道要放在**公有**子網路），私有子網路的路由表有沒有 `0.0.0.0/0` 指向 NAT；Google Cloud 檢查 Cloud NAT 的設定。
- 也確認出站的安全群組、防火牆規則沒有擋住。

複習：虛擬網路

</Answer>

### 改了 DNS 紀錄一段時間了，有些使用者還是連到舊的伺服器

<Answer>

- 解析器會依紀錄的 **TTL** 快取答案，舊的 TTL 還沒過期的使用者會繼續拿到舊的位址。
- 預防：切換前先把 TTL 調短，等舊的 TTL 過了再改紀錄；切換期間讓舊伺服器繼續運作一陣子。

複習：DNS 與 CDN

</Answer>

### 同一筆訂單被處理了兩次，客戶被扣了兩次款

<Answer>

- 可能原因：處理時間比 SQS 的**可見性逾時**長（預設 30 秒），還沒處理完訊息就重新可見，被另一個消費者拿走；或是至少傳送一次本來就可能重複。
- 修正：把可見性逾時調長到超過處理時間；**更重要的是讓處理冪等**，例如用訂單編號檢查是否已經扣款。

複習：訊息佇列

</Answer>

### 新建立的 EKS 叢集，部署後 Pod 一直停在 Pending

<Answer>

- Pending 代表 Pod 還沒被排到任何節點上。EKS 標準模式建好叢集後**還沒有節點**，要建立節點群組才會開始執行（Autopilot 和 EKS Auto Mode 則會自動處理節點）。
- 用 `kubectl describe pod` 看事件，找出排程失敗的原因。

複習：Kubernetes

</Answer>

### 把 SQS 佇列訂閱到 SNS 主題（或設定 S3 事件通知），訊息卻沒有進到佇列

<Answer>

- 佇列的**存取政策**要允許該服務送訊息：SNS 主題要允許 `sns.amazonaws.com`，S3 事件通知要允許 `s3.amazonaws.com`，並用 `aws:SourceArn` 限定來源。
- S3 在設定通知時就會先驗證，沒有權限會直接失敗；SNS 則是發布後默默送不進去。

複習：訊息佇列、案例：資料管線

</Answer>

## 行為題

行為題看的是你怎麼和人合作、怎麼處理壓力和錯誤。用 **STAR** 架構組織回答：

- **S**ituation（情境）：當時的背景。
- **T**ask（任務）：你負責什麼。
- **A**ction（行動）：**你**做了什麼（不是「我們」）。
- **R**esult（結果）：結果如何，最好有數字；學到了什麼。

常見題目與準備方向：

- **說說你處理過的一次服務中斷**：怎麼發現、怎麼止血、怎麼找出根本原因、之後做了什麼改進避免再發生。事故檢討的重點是改進流程和系統，而不是追究個人。
- **你犯過的一個錯誤**：誠實說明，重點放在你怎麼補救、學到什麼、怎麼避免別人再犯。
- **和同事意見不同時怎麼辦**：用資料和實驗說話，例如先做小規模測試再決定。
- **怎麼學習新技術**：舉一個具體的例子，例如用這個網站的 Lab 練習了什麼。

## 面試前的準備清單

- 每個觀念題都能用自己的話在一分鐘內講清楚。
- 至少準備兩個情境設計題的完整思路，練習邊畫圖邊說明。
- 準備三到五個 STAR 故事：一次事故、一次錯誤、一次合作、一次學習。
- 把這個網站的 Lab 做一遍：實際下過指令，比只讀文件更容易說清楚。
- 準備要問面試官的問題，例如團隊怎麼值班、怎麼部署、怎麼做事故檢討。

## 重點整理

- 四種題型：觀念、情境設計、故障排除、行為。
- 觀念題：一句話定義 → 差別或用途 → 例子。
- 情境設計題：先問需求，從最簡單的版本開始，逐層改進，主動說明取捨。
- 故障排除題：確認範圍，沿著請求路徑由外往內查，看證據，一次改一個地方。
- 行為題：用 STAR 架構，說清楚**你**做了什麼和結果。
